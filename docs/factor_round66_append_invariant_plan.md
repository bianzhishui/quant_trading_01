## 1. 问题

`write_full_daily` 的合并语义：

```python
prev = pd.read_parquet(path)
merged = pd.concat([prev, merged], ignore_index=True)          # prev 在前
merged = merged.drop_duplicates(subset=["date", "code"])       # keep="first" → 旧行胜出
merged.to_parquet(tmp, index=False); os.replace(tmp, path)     # 整分区原子重写
```

**按代码审查结论：新抓的数据不会覆盖历史行**（`keep="first"`）。
但这条"历史不被改写"的性质**从未被测试固定过**，且有两处真实风险敞口：

1. `drop_duplicates` 用的是**默认 `keep="first"`**——语义正确但**隐式**：
   任何人把它改成 `keep="last"`（或调换 `concat` 顺序）都会静默开始
   用新数据覆盖历史，且**没有任何测试会失败**；
2. **重复抓取同一天**（`fetch_daily_incremental` 的 `todo` 理论上会跳过已有 code，
   但手工/异常路径可能重发）→ 依赖 `keep="first"` 才幂等。

**这是 R56/R57 那类"面板被重写污染"事故的同类风险**：一旦发生，历史数字静默失真，
且 `data/fundamental/*` 在 `.gitignore` 里（**无快照可回溯**，本轮已确认）。

> **那 0.009% 残差本身不追**：无快照不可复原，且量级远小于材料性差异（0.24/0.35pp）。
> 本轮的交付物是**让这类问题下次立刻暴露**的不变量护栏。

---

## 2. 规则（定死）

**只新增测试，不改任何生产代码**。护栏内容：

1. 用**合成数据**在临时目录（`paths.full_dir` 指向 `tmp_path`）验证：
   - **L1**：对已有分区追加**新日期** → 既有 `(date, code)` 行的**值逐位不变**，行数 = 旧 + 新；
   - **L2**：**重复追加同一天两次** → 结果与只追加一次**逐位相同**（幂等）；
2. **L3 判别力自证**：同一合成输入下，用 `keep="last"`（覆盖语义）的朴素合并
   **必然改动历史行**，而生产语义不会 —— 断言"旧写法必然违规"；
3. **L4 真实分区门（`slow`）**：把真实 `full_daily/2026.parquet` **复制**到临时目录，
   再把该分区自身的 10-08 行（读自真实文件）重新追加一次 →
   全部既有行逐位不变、行数不变。**只在副本上写，绝不碰真实数据文件**。

---

## 3. 预注册判定标准

| 判据 | 标准 | 含义 |
|---|---|---|
| **L1 追加不改历史** | 合成：既有行值逐位不变；行数 = 旧 + 新增 | 主目标 |
| **L2 幂等** | 同日重复追加两次 == 追加一次（逐位） | 防重复抓取破坏 |
| **L3 判别力自证** | `keep="last"` 在**同输入**下必然覆盖历史（断言其 `close` 变成新值）；生产语义保留旧值 | R57/R58 教训：判据必须有判别力 |
| **L4 真实分区门** | 副本上重新追加 10-08 → 既有 579,943 行逐位不变、行数不变 | 端到端，真数据只在副本上写 |
| **L5 质量门** | `ruff check .` 0 错误 + `pytest` 全过（默认 + `-m slow`） | 仓库硬性要求 |

---

## 4. 诚实风险

1. **护栏证明的是"当前实现不改历史"，不能回溯解释那 0.009% 残差**
   —— 该残差的归因仍为**未定**，如实保留为待查；
2. **dtype 层面可能有差异**（`date` 的 `datetime64[us]` vs `ns`）：整分区重写会改变存储精度，
   但**不改数值**。若无害，测试对 `date` 列按数值比较并**显式记录该差异**；
3. **L4 依赖当前真实分区的存在**；文件缺失时 `skip`（不虚报通过）。

## §0 实施结果归档

> 实施 2026-10-09 ｜ 仅新增 `tests/test_full_daily_append_invariant.py`（**零生产代码改动**）

### 0.0 总判定：**✅ 通过（L1-L5 全过）**

| 判据 | 结果 |
|---|---|
| **L1 追加不改历史** | ✅ 追加新日期 + **同日重复发一次已有日期** → 行数 = 旧 + 新（重复日不新增），既有行 `close` 保持 10.0 **未被新值 999.0 覆盖**，逐位等于追加前 |
| **L2 幂等** | ✅ 同日重复追加两次 == 追加一次（逐位） |
| **L3 判别力自证** | ✅ 同输入下 `keep="last"` **必然**把历史 `close` 覆盖成 99.0，`keep="first"` 保留 10.0；两者不等 → 判据有判别力 |
| **L4 真实分区门（slow）** | ✅ 真实 `2026.parquet`（579,943 行）**复制**到临时目录后重新追加其 10-08 行（3,182 行）→ **行数不变 579,943**，**576,761 行既有数据逐位不变（含 dtype）** |
| **L5 质量门** | ✅ `ruff check .` 0 错误；`pytest` **65 passed**（默认）+ **5 passed**（`-m slow`） |

### 0.1 结论：追加路径**经证明**不会改动历史

- `write_full_daily` = `concat([prev, new])` → `drop_duplicates(keep="first")` → 整分区原子重写；
  **`prev` 在前 + `keep="first"` ⇒ 新数据不可能覆盖历史行**，且重复追加幂等；
- 顺带查证：**`write_full_daily_replace`（替换语义，会覆盖历史）是死代码，全仓无调用方**；
  三个写入方（`fetch_daily_incremental` / `fetch_full_market` / `fetch_delisted_daily`）
  **全部**使用安全的合并语义 → **不存在"替换式覆盖历史"的代码路径**。

### 0.2 关于那 0.009% 残差（**不追了，如实记录**）

排除法已经把范围收窄：

| 候选 | 结论 |
|---|---|
| 每日追加覆盖历史 | ❌ **已排除**（L4 证明逐位不变） |
| `write_full_daily_replace` 替换式写入 | ❌ **已排除**（死代码，无调用方） |
| 09-22 `industry_full` 刷新 | 已量化（R65：解释 99.8%） |
| **09-22 合法补数据**（退市股日线补抓 `fetch_delisted_daily` + 行业补全） | ⚠️ **最可能，但未证实** |

- `data/fundamental/*` 在 `.gitignore` 里 → **无历史快照，该残差不可复原**；
- 实测当前 2026 分区仅 **15 只** code 的数据止于 2026-09-01 之前（退市/长期停牌），
  量级上足以造成 0.009% 的池成员微变；
- **量级判断：不影响任何结论**（材料性差异是 R65 的 0.24/0.35pp，比它大 25~40 倍）。

### 0.3 遗留（建议另开一轮）

`write_full_daily` 的 `keep="first"` 目前是**隐式**语义——本轮用测试把它固定住了，
但代码本身没写明"这是有意为之"。建议显式化：

```python
.drop_duplicates(subset=["date", "code"], keep="first")  # 显式: 历史优先, 新数据不得覆盖
```
并顺手删除或标注死代码 `write_full_daily_replace`（避免将来有人误用替换语义）。
